## Confirmed platform issues / surprises

1. **Endpoint paths in the starter doc are wrong.** Doc says `POST /app/{orgCode}/{entityName}`, `GET /app/{orgCode}/{entityName}/{id}`, list via `/app/{orgCode}/{entityName}/list/{endpointName}`. Real paths: `/create/{entity}`, `/item/{entity}/{id}`, `/update/{entity}/{id}`, `/delete/{entity}/{id}`, `/list/{entity}` (filtered by query params, no named sub-path).

2. **`lookup` colType is undocumented.** Real, working relation-field type (used for `project_id` on child entities) but absent from the doc's colType enum (`string | number | boolean | date | enum | guid | autoincrement | formula | encrypted | file | s3`).

3. **Auto-generated base fields aren't documented.** Every entity silently gets `id`, `name`, `active`, `created_at`, `updated_at` — plus `user_id` if an owner index is configured. The doc's `entitySchemaShape` implies you define every field yourself.

4. **Owner index behavior is a real functional requirement, not a naming choice.** The owner field must be named exactly `user_id` for the platform to auto-stamp the signed-in user's id on create. Any other name (e.g. `ownerId`) is never auto-populated — confirmed via the full-build doc's `ownerIndex.behaviour` note, and via a live mistake in this project where we initially used `ownerId` and had to correct it.

5. **s3 field config UI doesn't match the doc.** Doc describes `s3ContentType: url | raw | json | json+staticKey | json+dynamicKey` set directly on the field. Real console UI: S3 key template, a **Content type** dropdown (JSON/CSV/Plain text/PDF/JPEG/PNG/Binary), and a separate **"What to store in S3"** toggle (Input field value vs. Entire record).

6. **Column type availability is split across two undocumented UI surfaces.** The quick "Add Additional params" modal only offers `number/boolean/date/string/encrypted`. `enum`, `lookup`, `s3`, `guid`, `autoincrement`, `formula`, `file` only appear in a separate, fuller per-field editor reached after initial field creation.

7. **Custom field names silently normalize to snake_case**, regardless of what's typed into the entity builder's "Input name" box (e.g. typing `htmlContent` saves as `html_content`). Confirmed via the API Studio test console's auto-generated placeholder request body, which reflects the real saved schema.

8. **Entity names normalize differently than field names** — PascalCase entity names (e.g. `GeneratedHTML`) get lowercased with separators stripped entirely (`generatedhtml`), not converted to snake_case (`generated_html`). Two different normalization rules for two similar-looking naming decisions, with no shared logic and no documentation of either.

9. ~~`eventType: "block"` (direct logicblock invocation from an event) does not exist.~~ **Correction: it exists as "block invocation," but only appears in Step 4's action list once at least one logicblock already exists in the org.** The action grid we screenshotted earlier (Entity automation, Webhook, Email, Slack, Salesforce, HubSpot, Stripe, Zapier, Twilio SMS, Microsoft Teams, Amazon S3) was captured before any logicblock had been created — the option is populated dynamically, the same way the lookup wizard's "Lookup API" dropdown only lists real `get-{entity}` APIs that already exist. The internal `event_type` value for this action is `custom_api`. Worth documenting this dependency explicitly rather than letting it look like a fixed, exhaustive list.

10. **The Webhook event action doesn't accept a literal URL.** It POSTs to `{{credential.base_url}}`, sourced from a tenant-configured connector credential (Settings → Integrations), not a URL typed into the event itself.

11. **Event entry_conditions are AND-only, with no "IN"/OR operator.** Can't gate a single event on "status is one of N values" — either use N separate events or drop the condition and branch on the payload downstream.

12. **`rolesAndAcl` is documented as `"status": "placeholder" / coming soon`, but is fully shipped** as a real IAM-style policy engine: named policies → statements → Effect (Allow/Deny) → entity-scoped GET/LIST/CREATE/UPDATE/DELETE checkboxes (saved as concatenated action strings like `getproject`) → resources array → IAM-style conditions (operator + condition key + values). Built-in template policies (`adminacl`, `memberacl`, `vieweracl`) already exist.

13. **Each entity's separate generated CRUD endpoints don't share field-projection config.** `create-{entity}`, `get-{entity}`, `update-{entity}`, `list-{entity}` each keep an independent copy of their field projections. Confirmed bug: `get-generatedhtml`'s Default view had stale projection names (`htmlcontent`, `projectId`) left over from before the snake_case normalization, silently returning `null` for those fields with no error — even though the entity schema and `create-generatedhtml` had the correct names (`html_content`, `project_id`) the whole time. Fixed by manually correcting the projection's `Name` field. No validation warning exists when a projection name doesn't match any real column.

14. **Agent crews are a separate config surface from logicblocks/events**, with their own Trigger types: `Manual`, `Scheduled`, `Webhook`, `Connector event`. No direct "on entity update" trigger — same limitation as events. Crews get entities attached as read-only "data source" tools, plus connectors, logic nodes (Condition/Loop/Human Gate/Parallel/Merge), and output nodes (JSON Response/Notification/Store to Table).

15. **The entity-suggestion ("auto-generate entities") feature produces incomplete/inconsistent specs**: `enum` fields with no `enumValues`, no owner index on the parent entity, `lookup` fields with no target entity specified, and PascalCase names that don't match either of the platform's real normalization rules (issue #7/#8).

16. **Chat/session memory doesn't persist in nostackai's own AI assistant** — past queries and context don't save, which is why this entire project had to be reconstructed from a pasted chat transcript instead of continuing a session.

17. **Known field-name bug on profile update**: docs say `picture`, live API actually expects `picurl`.

18. **The `lookup` colType has two completely different configuration UIs depending on which endpoint you're editing.** On `create-{entity}`, a `lookup` field is configured with a single, simple "target entity" selector (a gear icon next to the field, pick the entity — e.g. Project). On `get-{entity}`/`list-{entity}` (and presumably `update-{entity}`/`delete-{entity}`), the same colType instead requires the full 4-step lookup wizard (Source Id → Lookup API → Dest ID → Return field). Same field, same colType, two unrelated config surfaces with no indication they're connected — the simple create-side config doesn't carry over to the get/list side at all, so each endpoint's lookup has to be configured from scratch. Should be unified into one config (ideally the full 4-step version, since it's the only one expressive enough to actually resolve and return real data) shared across every endpoint for that field.

19. **Dragging one of the left-panel block options (in the logicblock builder) to the browser's search/address bar to open it in a new tab forces a re-login.** Presumably the drag interaction carries a URL or token-bearing payload that isn't handled correctly when dropped outside the app's own canvas, invalidating the current session. Minor, but disruptive mid-build — worth fixing since it interrupts logicblock construction work in progress.

20. **The internal `list_entities` step type (used inside logicblocks) was returning `{"items": [], "count": 0}` for a filter that had real, matching data via the direct REST `list` endpoint** — confirmed via a debug Response Shape mapping that dumped the LIST step's raw output. Ruled out as the cause: field-projection staleness (checked `list-generatedhtml`'s view, was correctly configured), the `items` vs `data` key naming (confirmed `items` was correct, it was just empty), and environment isolation (Test vs Production — disproven, since records created by the same logicblock run were visible via direct REST calls in real time). **This was a genuine, reproducible platform bug — since fixed server-side.** Re-confirmed working via the same debug technique after the fix landed. Reported by the user, verbatim, once the fix landed on the platform side:

    > no there was an issue with listing its just fixed now. this is something new

21b. **New fields added to an entity after initial creation don't propagate to the `update` endpoint's `UpdateParams` either — not just `get`/`list` projections.** When 5 new fields were added to `generatedhtml` (`sort_order`, `duration`, `transition`, `transition_duration`, `narration_text`), they showed up correctly in the `create` endpoint's `UpdateParams` (fields set at creation time apparently sync there), but were completely absent from the separate `update` endpoint's `UpdateParams` — meaning a PUT call setting any of those fields would have been silently ignored, not just misread. This is a worse variant of issue #13/#20: those were read-side (a GET/LIST returning `null` for a real value); this is write-side (an UPDATE call silently failing to persist a value at all, with no error). Confirmed and fixed by manually adding the 5 fields to the update endpoint's `UpdateParams` to match the create endpoint's. **Check every generated endpoint's config after adding a field to an existing entity — create, get, list, and update all keep independent copies, and none of them auto-sync from any of the others.**

21c. **Refinement to #21b, reported by the user directly after `interaction` (a brand-new entity) came through clean while `generatedhtml` (fields added after creation) did not.** The bug is specifically about fields added to an entity that already existed — not about entity creation itself. Quoted verbatim, as reported:

    > it did make it. when creating a brand new entity everything will be there. the issue occurs when updating an existing api

   Practical implication: a brand-new entity created with all its fields defined up front (e.g. `interaction`) does **not** need the manual per-endpoint create/get/list/update field check from #21b — every endpoint is generated correctly the first time. The check is only required when fields are added to an entity that was already live (e.g. `generatedhtml`'s 5 new fields, `voiceover`'s new `slide_id` field). This narrows #21b/#13/#20 from "any field change is suspect" to "only post-creation field additions are suspect" — a materially smaller, more targetable verification surface.

21. **Tenant's configured DeepSeek default model name (`deepseek-chat`) is invalid/deprecated.** An AI Call step inside a logicblock failed with: `OpenAI returned 400: "The supported API model names are deepseek-v4-pro or deepseek-v4-flash, but you passed deepseek-chat."` This had been silently masking behind issue #20 (the LIST bug) in every prior test — once the LIST bug was fixed, this became the new blocker. Because the AI Call step's failure is contained to its own step (`"on error": "halt"`) rather than failing the whole logicblock invocation, the block still returns `"status": "success"` at the top level with `null` result fields, making this look like a silent no-op rather than an obvious error. Fix: update the tenant's AI Provider settings (DeepSeek default model) to `deepseek-v4-pro` or `deepseek-v4-flash`, or set a valid model explicitly on the AI Call step's own Model tab.

22. **`transition` field's colType pattern across endpoints had to be corrected twice by the user, both times in their own exact words, before landing on the right rule.** First correction, after I had it as enum on every endpoint:

    > in everything except post, it should be stored as a string

   I read that as "enum only on `create`, `string` everywhere else including `update`" and revised accordingly — that was still wrong. Second correction:

    > well update also has enum

   Final, confirmed rule: `enum` (with the full `enumValues` list) on both write endpoints (`create` and `update`), plain `string` on both read endpoints (`get` and `list`). This is a specific instance of the general lookup/colType UI-fragmentation problem in issue #18 — nothing about the console flags which of the four endpoints should get which representation, so it has to be worked out per-field by trial and error.

23. **The Logic Blocks console's JSON tab wants the bare `steps` array, not the full block definition.** Pasting `{ name, method, type, enabled, onError, inputSchema, steps, outputShape }` (the shape `create_logicblock`'s MCP tool actually expects) into the console's JSON editor fails with `"JSON must be an array of step objects"`. The console splits that same information across separate UI surfaces instead: the `API name` text box (top), the `On error` dropdown (top right), a `Request schema` panel (left sidebar), and a `Response shape` panel (left sidebar) — only the bare `steps: [...]` array goes in the JSON tab itself. Two different serializations of the same underlying definition, undocumented which surface owns which field.

24. **Every step — including `condition` and `end`, which don't naturally produce one value — requires an `outputAs` field**, or the console rejects the whole array with `Step "sX" is missing required "outputAs" field"`. `get_platform_capabilities`' `logicblockStepTypes` list doesn't flag this as universal; discovered by trial and error against the live console validator, not from any documented schema.

25. **`condition` steps additionally require a `config` object to be present** (`{}` is sufficient), separate from and in addition to their `branches`/`defaultThen`/`steps` fields, which live as siblings of `config`, not nested inside it. Omitting it fails with `Step "sX" is missing required "config" object"`. Combined with #24, a minimal valid `condition` step needs `id`, `type`, `outputAs`, `config: {}`, `branches`, and `defaultThen` all present — `get_platform_capabilities`' step type list only documents `type`, `supportsMultiBranch`, `operators`, and `supportsCustomLogicExpression` for `condition`, none of which mention `outputAs`/`config` being required.

26. **`event_type: "custom_api"` (block invocation from an event) is confirmed fully working, not just present in the UI** — resolves the remaining open half of issue #9. Created 5 of these live via `mcp__nostackai__create_event` with zero errors: `destination_config = { target_entity: "<logicblock apiname>", field_mapping: { "<destKey>": "<value>" } }`, where a query-sourced logicblock input `foo` gets destKey `"_query.foo"` and the value `"source.id"` copies the triggering record's own `id` field into it (per the `fieldMappingGuide` in `get_platform_capabilities`, which turned out to be accurate here). `entry_conditions: [{ field, operator, value }]` gated cleanly on `status == "some_value"` with no issues.

27. **There is no `update_entity` or `delete_entity` MCP tool** — only `create_entity`, `describe_entity`, `list_entities` exist for entity schema management (compare to logicblocks, which do have `update_logicblock`/`delete_logicblock`, and events, which have `update_event`/`delete_event`). `create_entity` does not upsert either — calling it again on an existing entity name fails outright with `Entity "project" already exists`, rather than merging or replacing. The only way to change an existing entity's fields is a manual console edit, or (if no real data exists yet) manually deleting it in the console first and recreating via `create_entity`.

28. **`create_entity`'s `ownerIndexes` parameter isn't part of its declared tool schema** (only `entityName`, `UpdateParams`, `baseKeys`, `entityIdFieldName`, `IndexFields`, `Views`, `PublicOperations` are declared) **but the tool accepts it anyway** (its schema sets `additionalProperties: true`) **and silently mis-stores it as a raw stringified JSON blob instead of structured config** — no error, no warning, and `describe_entity` echoes the same broken stringified value back, so it looks superficially present. Net effect: owner-scoping silently doesn't work (no `user_id` auto-stamp on create, no functional `by-owner` index) until fixed manually in the console's Owner Index screen and re-verified via a fresh `describe_entity` call, which does return a proper structured array once fixed that way. Lesson: don't trust an extra/undeclared param on an `additionalProperties: true` tool just because the call doesn't error — verify the round-trip shape via a follow-up describe/list call.

29. **Blocks are difficult to move around in the Logic Blocks canvas view.** Repositioning a step node is fiddly/imprecise in the drag-and-drop canvas UI — reported directly by the user while manually laying out `generate_storyboard_draft`'s condition branches.

30. **The step-by-step (nested) view balloons the UI by roughly 2000% when hovering over a nested block.** Hovering a step nested inside a `condition`/`loop` in the canvas view triggers a massive, apparently unintentional scale-up of the hovered element — reported directly by the user, encountered while inspecting `generate_storyboard_draft`'s branch structure.

31. **The MCP tool surface has no way to actually execute/test a logicblock.** `create_logicblock`/`update_logicblock`/`describe_logicblock`/`delete_logicblock`/`toggle_logicblock`/`list_logicblocks` exist, but there is no `run`/`test`/`invoke` equivalent — confirmed by searching the full available tool set. The only way to see a logicblock's real execution trace (per-step status/timing/error, or a step's actual output value) is the console's own Logic Blocks editor Test Runner panel; calling the live endpoint directly only returns whatever the block's final `end` step's `response` is configured to include, which by design usually omits intermediate step data. Worth requesting a `run_logicblock`-style MCP tool that returns the full `execution.steps[]` trace, matching what the console's Test Runner shows.

32. **Dragging a sidebar nav item (not just a step-palette block, see issue #19) to the browser's address bar to open a new tab, or middle-clicking it, forces a re-login instead of opening the target page.** Reported directly by the user: attempting to open Data Manager in a new tab while working in Logic Blocks (via middle-click or dragging the nav link to the address bar) lands on the login page instead. Same underlying symptom as #19 (session gets invalidated by a drag/new-tab interaction the console doesn't handle correctly), but from a different trigger element — #19 was specifically the step-palette block options inside the Logic Blocks builder; this is the persistent left-hand app sidebar (Dashboard/API Studio/Logic Blocks/Data Manager/etc.), reproducible from at least the Logic Blocks page. Suggests the bug isn't scoped to the step palette specifically but to how this console handles any dragged-link-or-middle-click new-tab open in general.

33. **An event's "Disable" button deletes the event outright instead of disabling it.** Reported directly by the user, verbatim: "i clicked the disable button and i guess it got deleted." `ingest_source_on_create` (the `contentsource`-create event invoking `ingest`) was fully gone from `list_events` immediately after — not present with `enabled: false`, just entirely absent, same as a real `delete_event` call. Every `create_event`/`update_event` response confirms `enabled` is a real, settable boolean field on the event object, so a working disable-without-delete is clearly supported by the data model — the console's own "Disable" control just isn't wired to set `enabled: false`, it's wired to delete. High-severity: unlike most of these console quirks, this one is silently destructive and looks identical to the intended "temporarily turn this off" action right up until you notice the event is gone, not paused. Recreating a deleted event also does not retroactively reprocess anything that happened while it was missing (same caveat as issue with `ingest_source_on_create`'s earlier mis-wiring) — any records created in the gap need manual reprocessing.

34. **The canvas view's "Collection to iterate" dropdown (on a `loop` step) doesn't list `ai_call` step outputs as selectable options — only step types the UI recognizes as producing a plain collection (e.g. a `list_entities` step's output) show up.** On `generate_storyboard_draft`'s `slides_loop` step (meant to iterate `slides_result.slides`, the output of the `ai_call` step `s6`), opening the dropdown to see why no iterations were showing offered only one visible option: `sources` (the `list_entities` step earlier in the flow). The user clicked it to investigate — reported directly, verbatim: "When i go to the logicblock, no iterations are showing except sources so i just clicked it..." — and that single click silently overwrote the step's correct `listRef` (`"slides_result.slides"`) with `"sources"`, repointing the slide-creation loop at the raw content-sources list instead of the AI-generated slides array. A second loop step (`source_loop`) was also affected the same way (`"sources.items"` → `"sources"`), and separately, both `end` steps' `response` objects (confirmed present via `describe_logicblock` beforehand) were gone after this — whether that's the same root cause or a second effect of the same interaction wasn't isolated. High-severity because the failure mode looks identical to a legitimate config problem (an empty dropdown, nothing obviously "selected") right up until you click to explore it, at which point exploring becomes overwriting, with no confirmation, warning, or way to tell beforehand that a field reference the UI can't represent (a dotted sub-path into an `ai_call`'s declared JSON output) will be silently destroyed by opening its own picker. Restored via a full `update_logicblock` call re-asserting every step from a known-good source of truth (this project's local `logicblocks.json`). **Practical rule going forward: don't open a loop step's "Collection to iterate" dropdown at all if its `listRef` references anything other than a `list_entities`/similar step's raw output — check via `describe_logicblock` instead, and if it must be inspected in the console, treat any click inside that dropdown as a write, not a read.**

35. **Correction to my own earlier (wrong) guidance, not a platform bug: an `ai_call` step's declared `outputFields` do NOT spread onto the `outputAs` variable directly — they're nested one level deeper, under a `.response` key, alongside `tokensUsed` and `usage` as siblings.** I had told the user `slides_result.slides` was the correct reference (misreading `get_platform_capabilities`' "outputFields spread FLAT at the top level" as meaning the absolute top level of `outputAs`). Confirmed wrong by the project's own debug data, collected weeks earlier during the `maxTokens` truncation investigation and overlooked until revisited: `debug_slides_result` was shaped `{ "response": { "_raw": "" }, "tokensUsed": 2896, "usage": {...} }` — `.response` is always present as a wrapper, both on the `{_raw}` failure fallback and (per the correction here) on a successful parse. The real reference was always `slides_result.response.slides`, not `slides_result.slides`. This was the actual reason `generate_storyboard_draft`'s slide-creation loop (`s7`) found nothing to iterate across multiple rounds of `maxTokens` tuning (issue not logged separately at the time, since it looked like an AI-output-quality/truncation problem rather than a wrong reference) — the fix for the real truncation case (raising `maxTokens`) was correct and necessary, but insufficient on its own, since `s7` was pointed at the wrong path regardless of whether the AI call succeeded. "Flat at the top level" in the capabilities doc should be read as "flat within `.response`," not "flat on `outputAs` itself" — worth it being stated unambiguously there.

## Recommendations for making the starter JSON / MCP clearer for an AI consumer

- **Ship real endpoint paths**, not assumed ones — the biggest single source of wasted work in this project was the create/get/update/list path mismatch (#1).
- **Document every real colType**, including `lookup`, and note which ones are only reachable via the full field editor vs. the quick-add modal (#2, #6).
- **Document the two field/entity naming normalization rules explicitly** — ideally make them consistent with each other, but at minimum tell the AI/developer what to expect so it doesn't have to discover it via a live 400/silent-null bug (#7, #8).
- **Document auto base fields and the `user_id` auto-stamp requirement** up front — this is easy to get wrong once and expensive to unwind after entities and frontend code exist (#3, #4).
- **Replace the `rolesAndAcl: "coming soon"` placeholder** with the real IAM-policy shape — it's fully built and materially different from a simple permissions array (#12).
- **Document the real event action list and the `credential.base_url` webhook mechanism**, and drop any implication that a logicblock can be invoked directly from an event (#9, #10).
- **Document the AND-only entry_conditions limitation** so automation designs don't get planned around an OR/IN capability that doesn't exist (#11).
- **Document agent crews as a distinct system from logicblocks/events**, with their own trigger types and node palette (#14).
- **Fix (or at least flag) the underlying product bug in #13** — a schema/field change should propagate to every generated endpoint's projections, or the console should warn when a projection's field name doesn't resolve to a real column. This is the kind of bug an AI consumer of the "full build" JSON has no way to detect except by testing every endpoint live.
- **Make the entity-suggestion feature's output complete or explicitly mark gaps** — silently omitting `enumValues`, owner indexes, and lookup targets produces a spec that looks done but isn't (#15).
- **Surface step-level failures inside a logicblock more visibly** — a failed AI Call step (#21) shouldn't be indistinguishable from a successful no-op at the top-level response. Either fail the whole invocation, or make step-level errors much harder to miss than digging through the `execution.steps[]` array.
- **Keep AI provider default model names current** — a stale/deprecated model name (#21) fails silently deep inside a step, costing significant debugging time before the actual error message is found.
- **Document that the Logic Blocks console JSON tab takes only the bare `steps` array**, not the full block definition the MCP `create_logicblock` tool expects — and document `outputAs`/`config` as required on every step type, including `condition` and `end` (#23, #24, #25).
- **Document the real `custom_api` event `field_mapping` destKey convention** (`_query.foo` / `_path.foo` per the logicblock's declared input source, values as `source.<field>`) as confirmed-working, not speculative — issue #9's remaining open question is now closed (#26).
- **Add `update_entity`/`delete_entity` MCP tools**, matching the update/delete coverage logicblocks and events already have — right now the only way to change a live entity's schema is a manual console edit or delete-and-recreate (#27).
- **Either declare `ownerIndexes` in `create_entity`'s schema and handle it as structured config, or reject unknown top-level properties outright** — silently accepting and mis-storing it as a stringified blob is the worst of both options, since it produces no error at call time and only surfaces as a functional bug (broken owner-scoping) discovered later (#28).

# Changes needed to the nostackai starter/full-build prompt (MCP)

Everything below is generic to the platform — none of it is specific to this project — and describes what should change in `nostackai-starter-prompt.json` / `nostackai-full-prompt.json` itself so an AI consuming it doesn't have to rediscover these gaps live against the console the way this project did. Organized by which section of the JSON needs to change; each item maps back to a numbered issue above where one exists.

## `howNostackaiWorks.crud` and `.list` — endpoint paths are wrong

The doc states:
- Create: `POST /app/{orgCode}/{entityName}`
- Update: `PUT /app/{orgCode}/{entityName}/{id}`
- Get: `GET /app/{orgCode}/{entityName}/{id}`
- Delete: `DELETE /app/{orgCode}/{entityName}/{id}`
- List: `GET /app/{orgCode}/{entityName}/list/{endpointName}`

The real, live paths are:
- Create: `POST /app/{orgCode}/create/{entityName}`
- Get: `GET /app/{orgCode}/item/{entityName}/{id}`
- Update: `PUT /app/{orgCode}/update/{entityName}/{id}`
- Delete: `DELETE /app/{orgCode}/delete/{entityName}/{id}`
- List: `GET /app/{orgCode}/list/{entityName}` — filtered by query params (`?by=`, `?fieldName=value`), not a named sub-path

This is the single highest-impact fix (issue #1). Any frontend generated from the documented paths alone is broken until someone diffs it against a live export.

## `columnTypes` — missing colType and inaccurate config flows

- **`lookup` is completely absent from the colType list** (`string | number | boolean | date | enum | guid | autoincrement | formula | encrypted | file | s3`), despite being a real, commonly-needed relation-field type for linking child records to a parent (issue #2). Needs its own full entry: config UI, what it returns on read, whether it auto-creates any parent-scoped list filter.
- **`s3` field config doesn't match the console** (issue #5). Doc describes `s3ContentType: url | raw | json | json+staticKey | json+dynamicKey` set directly on the field definition. The real console UI is a separate "S3 configuration" modal with: an S3 key template, a **Content type** dropdown (JSON / CSV / Plain text / PDF / JPEG / PNG / Binary — not the doc's projection-mode list), and a separate **"What to store in S3"** toggle (Input field value vs. Entire record). These read as two different mental models of the same feature.
- **Column type availability is split across two undocumented UI surfaces with no cross-reference** (issue #6). A quick "Add Additional params" modal only offers `number/boolean/date/string/encrypted`. `enum`, `lookup`, `s3`, `guid`, `autoincrement`, `formula`, `file` are only reachable through a separate, fuller per-field editor opened after the field already exists. The doc should say which types require which surface.
- **The `lookup` colType has two entirely different configuration UIs on different generated endpoints for the same field** (issue #18). On an entity's `create` endpoint, a lookup field gets a single "target entity" selector. On the `get`/`list` endpoints, the same field instead requires a 4-step wizard (Source Id → Lookup API → Dest ID → Return field). Same field, same colType, two unrelated config surfaces that don't share state — configuring it on create does not carry over to get/list. This should be unified into one config surface shared across every endpoint for that field.

## `columnTypes.indexes` — auto base fields and owner-field naming aren't documented

- **Every entity silently gets base fields the doc never mentions** (issue #3): `id`, `name`, `active`, `created_at`, `updated_at`. The doc's `entitySchemaShape` implies every field, including id/timestamps, must be explicitly defined — it should instead list these as always-present and explain what each defaults to.
- **The owner index's field-naming requirement is a functional requirement, not a naming convention, and the doc undersells this** (issue #4). The owner field must be named exactly `user_id` for the platform to auto-stamp the signed-in user's id on create. Any other field name is silently never auto-populated — the calling app must set it explicitly on every create call. The doc's `ownerIndex.example` uses `user_id` but doesn't say this naming is load-bearing; it reads like any name would work the same way.

## `logicblocks` — the step-type reference is missing entirely

The doc's `logicblocks` section is two sentences (`summary` + a note pointing at an "importManifest section" that isn't actually included in what's generated). It should instead document the real step types available in the visual builder: `GET`, `LIST`, `CREATE`, `UPDATE`, `DELETE` (data), `CONDITION`, `LOOP` (flow), `CREATE_VAR`, `SET_VAR` (variables), `FORMULA`, `TRANSFORM` (computation), `CONNECTOR`, `AI CALL` (integration) — including each step type's actual config shape (e.g. `list_entities` takes `attrFilters`, `sortBy`, `sortDir`, `limit`; `ai_call` takes `contextFields`, `instructions`, `intent`, `outputFormat`; `condition` takes a `then`/`else` branch structure with nested `steps`). Also document:
  - The **Request Schema** panel (declares a logicblock's expected input fields — body and query params, referenced inside the block as `{{input.fieldName}}` or `{{input._query.fieldName}}`) and the fact that if no input schema is declared, the block receives the full triggering record as `input` when invoked via an automation.
  - The **Response Shape** panel (maps response keys to step outputs; omitting it returns the last step's raw output).
  - That a logicblock's HTTP method (GET vs POST) is independently configurable and must match how callers invoke it, or they get a 405.
  - The **"Generate with AI"** feature for scaffolding a block from a plain-English description, and the fact that it accepts a JSON paste (via a `<> JSON` tab) as an alternative to manual step placement — including that pasted step JSON requires a unique `id` per step or it's rejected.

## `events` — several core mechanics are undocumented or wrong

- **A real event action exists to invoke a logicblock directly ("block invocation," internal `event_type: "custom_api"`), and it isn't in the documented `eventTypeReference` at all** (issue #9). The doc's list of supported `after`-stage types (`app.entity`, `external.webhook`, `external.connector`, `external.s3`, `notification.*`) is incomplete. Additionally, this action only appears as a selectable option in the console once at least one logicblock already exists in the org — the doc should call out that the action list is populated dynamically based on org state, not fixed.
- **`external.webhook`'s destination doesn't work the way the doc describes** (issue #10). The doc says `destination_config.url` is a literal URL string. The real console does not offer a URL field at all for this action — it POSTs to `{{credential.base_url}}`, sourced from a tenant-configured connector credential (via Settings → Integrations), not something typed into the event itself.
- **`entry_conditions` are AND-only, with no OR/IN operator, and the doc doesn't warn about this limitation's practical impact** (issue #11). There's no way to gate a single automation on "field is one of N values" — this has to be done with N separate automations, or by dropping the condition and branching downstream. Worth an explicit callout since it changes how automations should be designed, not just a note buried in the operator list.

## `rolesAndAcl` — marked as a placeholder, but it's fully shipped

The doc says `"status": "placeholder"` / "coming soon." The real feature is a complete IAM-style policy engine: named policies → statements → an Effect (Allow/Deny) → entity-scoped action checkboxes (GET/LIST/CREATE/UPDATE/DELETE, which save as concatenated strings like `getproject`) → a resources array (defaults to `["*"]`) → IAM-style conditions (operator + condition key + values, e.g. `StringLike` on `request.pathParameters.id`). Built-in template policies (`adminacl`, `memberacl`, `vieweracl`) already exist (issue #12). This entire section needs to be rewritten from scratch to match what's live — a flat permissions-array shape (which is what an AI would otherwise guess at, absent real documentation) is materially wrong.

## `agents` — under-documented as a distinct system

The doc's `agents` section describes only the two invocation endpoints. It's missing that agent crews are configured in a visual builder distinct from logicblocks (issue #14), with:
- Their own **Trigger** types: `Manual`, `Scheduled`, `Webhook`, `Connector event` — no direct "on entity update" trigger (same limitation as events).
- Entities attachable as read-only "data source" tools.
- A node palette of Logic nodes (Condition, Loop, Human Gate, Parallel, Merge) and Output nodes (JSON Response, Notification, Store to Table) distinct from the logicblock step palette.
- Crew-level settings: session TTL, max concurrent sessions.

## `aiProviders` — no mention that provider model names can silently go stale

Nothing in the doc warns that a tenant's configured `default_model` string can become invalid if the underlying provider deprecates/renames it (issue #21: a previously-working DeepSeek model name started returning a 400 from inside an AI Call step). Worth documenting that model-name validity isn't checked at configuration time, only at call time, and that a failure inside an AI Call step doesn't fail the whole logicblock invocation — it's silently absorbed unless the caller inspects the per-step `execution.steps[]` array. That last point is itself a product gap worth flagging: **a failed step inside a logicblock returns `"status": "success"` at the top level**, with the failure only visible in a nested array — this makes debugging materially harder than it needs to be and should either be surfaced more prominently or documented as expected behavior.

## General product bug worth flagging outside the doc itself

Each entity's separately-generated CRUD endpoints (`create-{entity}`, `get-{entity}`, `update-{entity}`, `list-{entity}`) keep independent copies of their field configuration — there is no single source of truth, and this affects both reads and writes (issues #13, #20, #21b):

- **Read side:** a field can be correctly configured on `create` and simultaneously stale/misnamed on `get`'s or `list`'s projection (observed directly: a projection referencing a field name from before a later snake_case normalization, silently returning `null` for that field on every read, with no error surfaced anywhere).
- **Write side, and worse:** adding new fields to an existing entity was observed to sync into the `create` endpoint's `UpdateParams` automatically, but **not** into the separate `update` endpoint's `UpdateParams` — meaning a PUT call setting one of those fields is silently ignored, not merely misread. This is a real data-loss risk, not just a display bug: a caller has no way to know their update didn't persist.
- **Scope, refined (issue #21c):** this bug is specific to fields added to an entity **after** it already existed. A brand-new entity, created with all of its fields defined at once, does not exhibit the bug — every generated endpoint is correctly synced from the start. Confirmed directly by the user, verbatim: "it did make it. when creating a brand new entity everything will be there. the issue occurs when updating an existing api." The doc/console should make this distinction explicit rather than leaving it to be discovered by comparing a fresh entity against a modified one.

Either field changes should propagate to every generated endpoint's config automatically, or the console should at minimum warn when a projection/param field name doesn't resolve to any real column on the entity, and warn when `create` and `update` disagree on which fields are acceptable.
